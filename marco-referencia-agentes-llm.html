01 · Alcance

Alcance y principios

Este marco describe la arquitectura lógica de un sistema que combina un modelo de lenguaje con instrucciones, memoria, herramientas y controles. Es portable entre runtimes: editores con agente integrado, asistentes en CI, bots en mensajería o servicios HTTP propios.

Incluye

  • Semántica de LLM, contexto y agente
  • Artefactos AGENTS.md y memory.md
  • Separación de capas y responsabilidades
  • Criterios de estabilización y gobernanza

Excluye

  • Benchmarking de proveedores
  • Diseño de fine-tuning / RLHF
  • Implementación específica de un SDK
  • Políticas legales o de compliance locales
Principio rector El valor del sistema no reside solo en el modelo, sino en la calidad del contexto inyectado, la delimitación de herramientas y la persistencia controlada de estado.
02 · Fundamentos

Modelos de lenguaje (LLM)

Un Large Language Model es una red neuronal entrenada para modelar la distribución condicional de tokens: dada una secuencia de entrada (prompt + contexto), estima la probabilidad del siguiente token y genera salida de forma autoregresiva.

Operacionalmente, el LLM actúa como un motor de transformación de contexto: consume texto estructurado (instrucciones, evidencia, historial, esquemas de tools) y produce texto accionable (respuestas, planes, llamadas a herramientas, parches).

Propiedades relevantes para ingeniería

PropiedadImplicación
Condicionalidad al prompt La calidad de salida es función directa del contexto suministrado.
Ventana de contexto finita Existe un presupuesto de tokens; el exceso se trunca o se compacta.
No determinismo controlable Parámetros de muestreo (temperature, top-p) alteran la distribución de salida.
Conocimiento paramétrico estático Lo aprendido en preentrenamiento no se actualiza por una conversación aislada.
Riesgo de alucinación Puede generar afirmaciones plausibles sin anclaje factual verificable.
03 · Identidad del modelo

Modelo, endpoint e instancia

Conviene separar tres niveles que suelen confundirse en operación:

NivelDefiniciónControl operativo
Familia / checkpoint Pesos y arquitectura (p. ej. una generación de un proveedor) Selección de capacidad, latencia y costo
Endpoint / deployment Servicio de inferencia con límites, región y cuenta Cuotas, SLA, residencia de datos
Instancia de runtime Sesión concreta: system prompt, tools habilitadas, política de temperatura Comportamiento reproducible del agente

Cambiar de checkpoint sin cambiar AGENTS.md/memory/tools produce un sistema distinto con la misma “caja” de producto. El marco trata el modelo como componente sustituible.

04 · Aprendizaje

Aprendizaje, adaptación y límites

“Aprendizaje” en sistemas LLM en producción no es un único mecanismo. Existen capas con cadencias y garantías distintas:

1. Preentrenamiento y alineación (offline)

Optimización de pesos sobre corpora masivos e instrucciones curadas (SFT, preference optimization, etc.). Define capacidades generales. No ocurre en el turno del usuario; es un proceso industrial del proveedor o del equipo que entrena el modelo.

2. Adaptación en contexto (in-context learning)

El modelo condiciona su salida a evidencia presente en la ventana: ejemplos few-shot, fragmentos de código, políticas, resultados de tools. Es la forma dominante de “personalización” en runtime. Es efímera: desaparece al truncar o cerrar la sesión si no se persiste fuera del modelo.

3. Adaptación persistente (artefactos externos)

Instrucciones versionadas (AGENTS.md), memoria operativa (memory.md), índices RAG, evaluadores y hooks. El sistema “aprende” a escala de organización porque el contexto se reconstruye de forma determinista en cada sesión.

Separación crítica No confundir actualización de pesos (entrenamiento) con actualización de contexto (operación). La mayoría de las mejoras de calidad en ingeniería de agentes provienen de la segunda.
05 · No determinismo

Estocasticidad de la generación

Dada una entrada aparentemente idéntica, las salidas pueden divergir. Las causas son estructurales, no anecdóticas:

Fuente de varianzaMecanismoMitigación
Muestreo Temperature / top-p / seeds no fijados Bajar temperatura; fijar seed si el API lo permite; pedir salidas estructuradas
Contexto no idéntico Historial, archivos abiertos, compactación, orden de tools Snapshots de contexto; prompts canónicos; aislamiento de sesión
Cambio de checkpoint Routing automático a otro modelo o versión Pinning explícito de modelo en config
Ambigüedad semántica Especificación incompleta ? múltiples soluciones válidas Contratos de salida, acceptance criteria, ejemplos gold
Herramientas no idempotentes Búsqueda, APIs, estado del repo Fixtures; captura de evidencia; deduplicación de side-effects

Para tareas críticas (seguridad, migraciones, contratos financieros), el marco exige verificación externa: tests, typecheck, revisores humanos o agentes de verificación con brief fijo. La generación no es la fuente de verdad.

07 · Agente

Arquitectura de agente

Un agente es un bucle controlado sobre un LLM con capacidad de invocar herramientas y reincorporar observaciones al contexto hasta satisfacer un criterio de terminación (éxito, presupuesto agotado, bloqueo de política).

Ciclo canónico

  1. Compose — ensamblar system/policy + memoria + objetivo + evidencia.
  2. Infer — el modelo produce plan, texto o tool-call.
  3. Execute — el runtime ejecuta tools bajo permisos.
  4. Observe — resultados (stdout, diffs, errores) vuelven al contexto.
  5. Decide — continuar, pedir clarificación, o terminar.

Responsabilidades del modelo

  • Clasificación y planificación
  • Síntesis y redacción
  • Selección de tools
  • Propuesta de cambios

Responsabilidades del runtime / código

  • AuthN/AuthZ y secretos
  • Idempotencia y dedupe
  • Límites duros (red, FS, red)
  • Persistencia de estado
Regla de diseño Lo no seguro de repetir o de errar no debe depender solo del juicio del modelo. Debe vivir en código, policies o hooks.
08 · Política

AGENTS.md — política del sistema

AGENTS.md es el artefacto versionado que define la política operativa estable del agente respecto a un repositorio o dominio. Equivale, en otros runtimes, a project instructions, rules always-on o system prompts de producto; el nombre canónico de este marco es AGENTS.md.

Contrato de contenido

SecciónPropósitoCriterio de calidad
Objetivos y no-objetivos Delimitar el mandato del agente Explícito; sin ambigüedad de alcance
Comandos canónicos Build, test, lint, deploy locales Copiables; un camino oficial por acción
Arquitectura Límites de módulos y ownership Punteros a paths canónicos, no essays
Estilo y invariantes Convenciones no cubiertas por linter Corto; complementa tooling, no lo reemplaza
Guardrails Paths prohibidos, datos sensibles, acciones de riesgo Machine-actionable cuando sea posible 
# AGENTS.md

## Mandato
- Implementar cambios en este monorepo siguiendo los contratos de /packages/api.
- No modificar /infra/prod sin aprobación explícita en el prompt.

## Comandos
- test: pnpm -w test
- typecheck: pnpm -w typecheck
- e2e: pnpm --filter web e2e

## Invariantes
- Domain logic en packages/domain; adapters en packages/adapters
- Errores de API tipados; no strings mágicos en boundaries

## Guardrails
- Prohibido commit de .env*, secretos o dumps
- No ejecutar migrate en producción desde el agente

AGENTS.md anidados por subdirectorio permiten especialización; la política más específica al path de trabajo prevalece en caso de conflicto.

09 · Estado

memory.md — estado persistente

memory.md representa el estado operativo acumulado que debe sobrevivir entre sesiones: decisiones, hallazgos, preferencias de trabajo y trampas conocidas. Complementa a AGENTS.md; no lo duplica.

DimensiónAGENTS.mdmemory.md
Semántica Política estable del sistema Estado y aprendizaje operativo
Cadencia de cambio Baja (PR consciente) Alta (append / compactación)
Audiencia Todo el equipo / todo agente Sesiones posteriores del dominio
Fallo si falta Inconsistencia de estilo y proceso Re-descubrimiento costoso; regresiones de criterio

- regenerar Prisma sin revisar migrations rompe shadow DB

## Preferencias de interacción
- Diffs pequeños y revisables; no reescrituras masivas no solicitadas
- Idioma de respuestas: español técnico

## Estado de trabajo
- WIP: migración checkout v2 (rama feat/checkout-v2)
- Bloqueado: e2e flaky en safari — issue #842

Gobernanza de memoria

  • Prohibido persistir secretos, PII o tokens.
  • Toda entrada debe ser falsable o fechable; las obsoletas se archivan o eliminan.
  • Cuando el archivo crezca, compactar a un resumen con punteros a issues/PRs.
  • Si el runtime ofrece Memory UI o store KV, aplicar el mismo contrato semántico.

11 · Operación

Modelo operativo

  1. Baseline de política — publicar AGENTS.md mínimo (comandos, invariantes, guardrails) en el repo.
  2. Pinning de modelo — fijar checkpoint para tareas críticas; documentar excepciones.
  3. Memoria operativa — introducir memory.md (o store equivalente) con esquema de secciones y reglas de higiene.
  4. Procedimientos reutilizables — extraer workflows recurrentes a skills/playbooks invocable bajo demanda.
  5. Surface de tools mínima — habilitar solo capacidades necesarias; denegar por defecto lo destructivo.
  6. Verificación — tests/typecheck como gate; evals de regresión para prompts críticos.
  7. Observabilidad — registrar tool-calls, costos y fallos de política; no registrar secretos.
Criterio de madurez Un sistema es maduro cuando un cambio de proveedor de LLM no obliga a reescribir el proceso de trabajo: solo se re-valida el pinning y las evals.
